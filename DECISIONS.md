# Decisions

## Layout

- `src/` is the crate `nanocode-swift` (`staticlib`): `bridge.rs` is the C ABI and its multi-threaded tokio runtime, `command.rs` the command table, `session.rs` the SDK's `TurnInbox<SessionLog<_>>` per open session over `sqlite.rs`'s `SqliteSql` (one `nanocode.sqlite` in the app's data directory holds every session's `SqlStore` state and `SessionLog`; the SDK dropped its SQLite host on 2026-11-08 in d326d01f0, when pyramid-core was its only remaining SQL user, so this crate keeps the last version of that host, `open_async` only, over rusqlite 0.38 with bundled SQLite, and existing `nanocode.sqlite` files open unchanged), `config.rs` the session configuration and model clients, `tools.rs` Swift host tools as the SDK's `FunctionTool`, `files.rs` a native `FileHost` for file tools, `shell.rs` the simulated bash (see Simulated shell), `hand.rs` hands, `payments.rs` and `wallet.rs` machine payments, and `catalog.rs` the model catalog.
- `include/` holds `nanocode.h` and the `NanocodeFFI` module map; `scripts/build-ffi.sh` builds the crate for `aarch64-apple-darwin` (and `x86_64-apple-darwin` with `UNIVERSAL=1`), `aarch64-apple-ios` and `aarch64-apple-ios-sim` (not `x86_64-apple-ios` since 2026-11-16: the SDK's own `libc` bindings in `nanocode-sys` cover iOS only on arm64, and `cargo check -p nanocode-sys --target x86_64-apple-ios` gives 261 errors, so the Intel iOS simulator is gone from the release) and writes `build/NanocodeFFI.xcframework`. It runs one `cargo build` for every target and copies into the XCFramework only the files whose contents changed (`rsync -c`), so a Rust change leaves its headers alone and Xcode relinks the apps without recompiling their Swift (10.6 s for the Mac demo, against 117 s when the XCFramework was written anew). `PROFILE` is `fast` by default: release dependencies, and this crate at `opt-level` 1 with 256 codegen units and incremental compilation (`--config profile.release.package.nanocode-swift.*`, so the dependencies keep their release builds); `PROFILE=release` builds this crate at `opt-level` 3 too, as `scripts/publish-ffi.sh` does, and `PROFILE=debug` builds unoptimized libraries (370 MB for macOS arm64 on 2026-10-27). `PLATFORMS="macos"` limits the platforms. The crate is a `staticlib` only: an `rlib` beside it spent about 10 s per build writing metadata nothing reads. Measured on 2026-10-29 for one edit to `src/shell.rs` (Apple silicon, under heavy load from other builds): a release build of the crate took 34 to 65 s, 41 s of it in LLVM's passes, 21 s in code generation and 10.5 s in metadata (`-Z time-passes`), and `PLATFORMS=macos scripts/build-ffi.sh` with `fast` took 36 s including that build. SwiftPM recompiles `Nanocode` and every module above it whenever the library changes (it lists the copied `libnanocode_swift.a` as an input of each Swift compile; 21 to 23 s for `Console`), while Xcode only relinks; a Swift edit in `NanocodeKit` took 12 s to rebuild the Mac demo in Debug and 18 s in Release.
- `NanocodeKit` is the UI, in AppKit on macOS and UIKit on iOS from one source (`KitView`, `KitColor` and `KitFont` alias the platform types; no SwiftUI): `CloneViewController` and `CloneNode` are nanocode-ts's ChatGPT and Claude clone apps (`src/react/clones/ChatGpt.tsx`, `Claude.tsx` and their CSS, as nanocode-vercel-durable's `/chatgpt` and `/claude` render them) with `Skin.chatgpt` and `Skin.claude` carrying their CSS variables in light and dark: the sidebar of chats with hover rows and delete, the header (ChatGPT's model menu, Claude's centered title), the hero with the greeting, composer, prompt pills and footer, the transcript (user bubble, grouped tool calls as ChatGPT's "Ran code" card or Claude's collapsed cells, thinking blocks, markdown with code bars and ruled tables, the pulse or spinning spark), the composer with attachments, steer and stop, and the model list, which opens below the ChatGPT header and above the Claude composer. `CloneProps` carries what the host supplies (conversations and callbacks, `ClonePicker`, prompts, footer markdown, header actions such as a `ClonePill`, `titlebarInset` for a full-size-content window). Below 768 points wide the layout follows the clones' mobile CSS: the sidebar becomes a drawer over a scrim, the header shows its open and new-chat buttons, the user bubble widens to 85% and the hero shrinks; on iOS it keeps to the safe area and above the keyboard. `NanocodeChatViewController` is the conversation alone for an app's own window. Views are `Node` subclasses that measure and place their children themselves (`Stack`, `Flow`, `Label`, `TextNode` on `NSTextView`/`UITextView` for selectable text, `ScrollNode`, `InputNode`), and `Observer` re-renders on `Chat`'s Observation changes. Check layouts at phone width with the demo's `-NanocodeWindow 390x844` (`-NanocodeBackground YES` keeps it from taking focus, `-NanocodeNew YES` opens a new chat, `-NanocodeStyle chatgpt|claude`, `-NanocodeAppearance light|dark`, and `-NanocodeType YES` types `-NanocodePrompt` into the composer before sending it, for recordings).
- `NanocodeDevice` (iOS and macOS; its sources are `#if os(iOS) || os(macOS)`) is an iPhone's or a Mac's tools and permissions for a hand, moved from gakonst/personal's `apple/App/Hand` (2026-11-01), which had ported and expanded `Examples/Demo/Shared/DeviceTools.swift`: `DeviceTools.all` (`open_url`, `speak`, `photos`, `listen`, `compose`, `camera`, `device_info`, `clipboard`, `screen`, `shortcut`, `files`, `speech`, `contacts`, `calendar`, `reminders`, `location`, `geofence`, `notification`, `motion`, `music`, `bluetooth`, `local_network`, `photo_library`, `wallet`, and `focus`, `health`, `home` and `nfc` when the binary is signed with their entitlement, which `Entitlements` reads from the running executable's code signature) and `DeviceCapability` (one per permission: label, group, description, the tools it gates, an SF Symbol and `reason`; `all`, `available`, `open`, `groups`, `named`, `permission(name)`, `system(name)` to ask iOS, and `hand(ask:)`, the `HandCapability`s a hand offers, asking the user through `ask` before the system prompt). An app calls `DeviceTools.configure(DeviceSettings(app:hand:scheme:appGroup:buildKey:reasons:composer:))` before building the tools: `app` is the name tool text and errors use ("needs Personal open"), `hand` the hand name a permission error tells the agent to ask through, `scheme` the URL scheme `shortcut` comes back on (the app passes opened URLs to `ShortcutCallbacks.handle`), `appGroup` the container `files` calls `group`, `buildKey` the Info.plist key `device_info` reports as `app_build`, `reasons` replaces a capability's default reason, and `composer` drafts messages and email (the `compose` tool is left out without one), so an app that avoids linking MessageUI at launch, as Personal does with its lazily loaded framework, keeps doing so. The package's iOS floor is 17, so iOS 18 and 26 APIs the tools used (`HKUnit.appleEffortScore`, `PKPass.relevantDates`, MapKit's `MKReverseGeocodingRequest` and `MKMapItem.location` and `address`) are taken when available, with `CLGeocoder`, `relevantDate` and placemarks before. Built with `xcodebuild -scheme NanocodeDevice -destination 'generic/platform=iOS Simulator'` against the release FFI (with `build/` moved aside and SwiftPM's manifest cache cleared, since the manifest picks `build/NanocodeFFI.xcframework`, which this Mac builds for macOS only, whenever it exists). On macOS (2026-11-01) the same tools build with AppKit where iOS uses UIKit (`DevicePresenter` is `UIViewController` or `NSWindow`, `DeviceTools.top()` the key window, `open` through `NSWorkspace`, the clipboard through `NSPasteboard`, `files`' pick, export and share through `NSOpenPanel`, `NSSavePanel` and `NSSharingServicePicker`, `shortcut` checks `NSWorkspace.urlForApplication`), and leave out what a Mac lacks: `camera`, `screen`, `motion`, `music`, `wallet`, `health`, `home` and `nfc` and their capabilities (`Health`, `Home`, `Media`, `MotionTools` and `Wallet` stay `#if os(iOS)`), and `authorizedWhenInUse`, which macOS does not have, so `location` there is granted only `authorizedAlways`. Tool text names the device as `DeviceTools.here` (iPhone or Mac) and its settings as `DeviceTools.settingsApp`. `DeviceTools.environment` is the `HandEnvironment` a hand reports (`ios` with the system name, version and model; `darwin` with the OS version string). `NanocodeDeviceCompose`, a sixth product, is `DeviceComposer.system`: MessageUI's message and mail sheets on iOS and `NSSharingService`'s compose email and message services on macOS, separate so an app such as Personal that loads MessageUI lazily does not link it. `Examples/Demo` uses only these: `DeviceTools.configure(DeviceSettings(app: "Nanocode", hand:, scheme: "nanocodedemo", composer: .system))`, `DeviceTools.all` for its sessions and hands, `DeviceCapability.hand` (granting the app's own prompt, so the system's asks) and `DeviceTools.environment`; it registers `nanocodedemo` and passes opened URLs to `ShortcutCallbacks.handle`, declares the Bonjour types `local_network` browses and the always-location and local-network usage strings, and its own `DemoTools` and `DeviceTools` copies are gone. `swift build` builds both products for macOS, and `xcodebuild` built `NanocodeDemo-macOS` and `NanocodeDemo-iOS` (simulator) against the release FFI. - `Package.swift` exports seven products (`NanocodeDevice` and `NanocodeDeviceCompose` above, `NanocodeComputer` below). `NanocodeCore` is plain Swift with no Rust: `JSON`, `LoggedEvent`, `LiveEvent` (nanocode-ts's `liveEvent`, plus `user` events from `input.accepted`), `Transcript` (nanocode-ts's `Transcript`: paced reveal, paragraphs, one `ToolCell` per call with nested Code Mode calls, yielded cells and their `wait`s), `ToolInput`, `Turn.group`, `Activity`, the markdown block parser with `MarkdownStream` (`complete`, `blocks`, and `lines`, `fences` and `test` for a host's own streaming views), `StreamingBlocks` (`blocks(complete(text))` for a reply that grows at its end, at a cost that does not grow with it: appending can only change where the last block starts, so every block before the last two is kept from the previous call and only the last is healed, and a rewrite or a link or footnote definition, which keeps a reply whole, starts over), `Highlight`'s tokenizer and `DataURL`. tempoxyz/pyramid's app takes the parser, the stream, `StreamingBlocks` and the tokenizer from here and keeps its own caches (a two-generation least-recently-used cache, so a streaming reply's versions never push finished blocks out) and its own SwiftUI views and colors. `NanocodeViews` is SwiftUI over it, also without Rust, kept for SwiftUI hosts such as tempoxyz/pyramid's app; this package's own UI and apps are AppKit and UIKit (`NanocodeKit`): `MarkdownView` with `MarkdownStream` and `Highlight` (ported from tempoxyz/pyramid's transcript), `CodeBlock`, `ToolCellView`, `ThinkingView`, `TranscriptView` over a `TranscriptState`, and `NanocodeTheme`. `Nanocode` is the runtime over the Rust library (`NanocodeRuntime`, `Session`, `Chat`, `Wallet`, `WalletMonitor`, `HandMonitor`, hands, runners, the model catalog). A host that renders nanocode events it receives some other way, such as from a server, uses only `NanocodeCore` and `NanocodeViews` and links no Rust. `NanocodeFFI` is the local XCFramework when `build/NanocodeFFI.xcframework` exists, else the release that `ffi-release.json` names (`url`, `checksum`, `fingerprint`), so apps depend on the package without building Rust. ## Bridge

`nanocode_start(config, length, callback, context)` starts a runtime for a data directory (`{"data_dir", "tempo_home"?}`), `nanocode_send(handle, bytes, length)` sends one command and `nanocode_stop(handle)` closes every session and hand and shuts the runtime down; it blocks, so Swift calls it from `deinit` off the main actor. Every message either way is one JSON object. Swift sends `{"id", "command": {"<name>": {fields}}}` (externally tagged, as nanocode-ts's commands) and gets `{"reply": id, "ok"}` or `{"reply": id, "error"}`; a command without `id` gets no reply. Rust sends `{"event": {"session", ...}}` (`logged` and `live` batches of the SDK's `LoggedEvent`s, `driving`, `turn` with the finished turn's report, `waiting`, `resumed`, `error`), `{"call": {"id", "kind": "tool", "body": {name, input, context}}}`, which Swift answers with the `reply` command, `{"hand": {"id", "event" | "stopped"}}` and `{"runner": ...}` alike, `{"wallet": {"prompt"}}`, `{"payments": {"status" | "notice"}}` and `{"log"}`. The callback runs on the runtime's threads; `Router` in `Runtime.swift` resolves replies and yields events into `AsyncStream`s synchronously, so a session's events stay in log order.

Commands: `models`, `sessions` (stored root sessions, newest first), `open` (a `Configuration`, see `config.rs`, which denies unknown fields), `close`, `submit`, `steer`, `move_queued`, `replace`, `cancel`, `turn`, `pending`, `page`, `settings`, `compact`, `checkpoint`, `permission_mode`, `settle`, `interrupt_subagent`, `close_subagent`, `reply`, `mcp_sign_in`, `mcp_sign_in_wait`, `plan_sign_in`, `plan_sign_in_complete`, `plan_status`, `plan_sign_out`, `hand_start`, `hand_stop`, `hand_status`, `runner_start`, `runner_stop`, `runner_status`, `shell_run`, `wallet_connect`, `wallet_use`, `wallet_forget`, `payments` and `funding_url`. `open` builds one `Nanocode` runtime per session (`without_runners`, the session's workspace or `<data_dir>/workspace`) and opens its `TurnInbox`; a driver task per session calls `TurnInbox::drive` whenever a submit wakes it, retries `Waiting` and `Interrupted` turns with a backoff from 0.5 s to 30 s, and reports each finished turn. An `open` with `fork` (`session`, an open session's id) starts a new session from that one's conversation through `Runtime::switch`, which forks it when the configuration keeps the model and otherwise carries its transcript to the configuration's model or provider; with `checkpoint` (from the `checkpoint` command, taken before a turn) and `before` (that turn's request id) it forks the conversation as it was before that turn. The new session gets its own ID, which the reply carries, a copy of the parent's log up to the fork point, and a place in `sessions`.

## Machine payments

`payments.rs` is gakonst/nanocode-machines's `nanocode-mpp` layer moved into a library: `Mpp` is a `nanocode::http::Layer` that runs mpp-rs's 402 flow (`send_with_exchange` over the layer's `Next`) against `openai.mpp.tempo.xyz` and `anthropic.mpp.tempo.xyz`, preconnects each service once per wallet, keeps prepaid vouchers (`PREPAID_REQUESTS`), and attaches an `EventHook` that hands `payment-need-voucher` and `payment-receipt` SSE events to the session provider, which consumes them so neither backend's parser sees them. Channels live in `<data_dir>/payments/channels.db`. Spend comes from mpp-rs's `ClientEvents` and reaches Swift as `payments` messages (`PaymentStatus`). Without a wallet a paid request fails before it is sent with `tempo_id_required`.

A wallet is an access key Tempo ID approved (2026-11-17, below): `wallet_connect` generates a secp256k1 key and runs Tempo ID's device grant natively as the unregistered CLI `cli:nanocode` (`POST https://id.tempo.xyz/device/code` with `scope=openid`, the device name, the key request as `key_authorization` and a funding hint of 2 MACH, then `/oauth2/token` polls with the device-code grant), with nanocode-ts's limits (2 MACH, and 0.1 USDC.e and 0.1 pathUSD for fees, one day; pathUSD since 2026-11-08, because Tempo takes no fee in MACH, which has no FeeAMM liquidity, and an account holding pathUSD but no USDC.e could not pay the fee that lands its key) and scopes (MACH `transferWithMemo` and its approval to the swapper, the swapper's `swapTo`, and the TIP-1034 escrow's open, top-up, close and withdraw). ## Computer use

`NanocodeComputer` (macOS; its sources are `#if os(macOS)`, Swift 5 language mode; no Rust, so it builds without the FFI) is computer use over Accessibility and ScreenCaptureKit served as an MCP server on stdio, moved from tempoxyz/pyramid's `PyramidComputer` on 2026-11-05, where Pyramid.app runs it as `Pyramid --computer mcp` for the `computer` tool of its Hand (pyramid-core's kernel-computer starts it as the default macOS provider). The token response's `key_authorization` is the Tempo node's RPC form, which tempo-primitives' `SignedKeyAuthorization` deserializes as is (camelCase, hex quantities, `keyType`, `allowedCalls` with `selectorRules`, `signature` tagged by `type`), so the bridge reads it straight into that type and checks its `keyId` and `chainId` before installing it; it no longer goes through tempo-alloy's `TempoAccountsKeyAuthorization`, whose RPC reader drops `allowedCalls`. `funding_url` opens `https://id.tempo.xyz/deposit?address=…&chain=4217&funding_hint=2&funding_token=MACH` (Tempo ID's deposit page, Buy MACH first) instead of Tempo Wallet's `/agent?action=fund`, and the device request carries the same funding hint, so Tempo ID offers to add MACH after the approval when the account holds less. The Tempo CLI path (`wallet_cli`, `Wallet.useTempoCLI()`, `WalletMonitor.useTempoCLI()`, `NanocodeRuntime(tempoHome:)`, the demo's `-NanocodeWallet cli` and the console's fallback) is removed rather than kept: it read `~/.tempo/wallet/store.json`, the store `tempo wallet login` writes, which is Tempo Wallet's own sign-in, and shared its channel store; the console now uses the key `Console wallet` saved, and the AppKit sample opens Tempo ID's approval page itself. `connect(name:)` drops `website` and `icon`, which only Tempo Wallet's connect dialog showed (Tempo ID's device page shows the `device` name), and the unsent-request error is `tempo_id_required` (no other repository reads this crate's code). An approval needs a person's passkey, so a full sign-in and a first paid request with a Tempo ID key are not yet tried, and the Swift package was not rebuilt here (no macOS).
